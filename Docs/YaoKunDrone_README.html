一、项目简介

耀坤飞控（YaoKunDrone）是一套完全自主研发的、基于 ESP32-S3 微控制器的四轴无人机飞控固件。它运行在 Arduino 框架上，把姿态解算、串级 PID 控制、安全保护、遥测上报和浏览器遥控界面整合进 5173 行可读性很强的 C/C++ 代码中，无需图形化上位机工具、无需专用地面站，一台手机连上飞机热点打开网页就能操控、调参、看状态。

这个项目的出发点不是做一个「能飞的玩具」，而是做一套能被完整读懂、能被放心修改的开源飞控教学与实践平台。因此代码里的每一个常数都有出处注释，每一处非直觉的设计都写清了「为什么这么写」和「不这么写会怎样」——它同时也是一份可运行的中文飞控教材。

当前固件版本 v1.1（2026-10-23），相对 v1.0 的三项变更（均由真机试飞问题驱动，详见对应章节）：① 关闭芯片欠压复位（brownout）——修复地面临界油门必重启的问题，见第七节；② 偏航环加入积分 Ki=0.005——消除电机/桨扭矩不对称导致的匀速自旋，见 5.5 节；③ 偏航扭矩符号适配（kYawTorqueSign）——适配实测电机布局，修复起飞加速自旋，见 5.3 节。

1.2 飞行能力定位（请先读这一段）

本机是「纯姿态自稳 + 手动油门」飞控，没有任何位置或速度传感器。

机身上只有一个六轴 IMU，没有 GPS、气压计、激光测距、光流、磁罗盘。所以：

能力说明
能做姿态自稳——松开摇杆时机体会自己把水平面稳住；横滚、俯仰、偏航三轴可控；油门手动。
不能做悬停定点。松杆时姿态被稳住，但会保持既有水平速度继续飘；松油门就掉高度。
因此飞行时需要持续微操修正，属于「运动相机式的手动飞行」体验，而非消费级无刷机的 GPS 定点体验。

想获得真正的定点悬停能力，需要接入激光测距（VL53L1X）+ 光流（PMW3901）——本工程已为此预留了 SPI 与第二组 I2C 引脚，详见 第十六节 扩展路线。

二、功能特征

2.1 飞行控制

串级双环控制

横滚与俯仰采用「角度外环 + 角速率内环」串级结构，偏航为单环角速率控制。500 Hz 固定周期调度。

X 型混控

四电机分处机臂对角，单电机故障时仍保留剩余推力与部分控制能力，容错优于 H 型。

低油门扭矩补偿

按油门线性缩放控制量，抵消电调线性区对操控性的侵蚀，悬停时仍能精细微调。

积分抗饱和

PID 输出触顶时积分项按 0.99 系数缓慢衰减，防止限幅期间积分失控，恢复后姿态猛甩。

2.2 姿态估计

  • 三套解算器可运行时切换：Madgwick 梯度下降、Mahony（Betaflight 式 PI 修正 DCM）、互补滤波，默认 Mahony。
  • 加速度计信任度自适应：实时计算 |a| 偏离 1g 的程度得到信任度，据此动态调整 Madgwick 的 β 或互补滤波的 α。剧烈机动或自由落体时滤波器自动退化为纯陀螺积分，不会被错误的重力方向带跑。
  • 三种 IMU 自动识别：MPU6050（I2C，WHO_AM_I = 0x68/0x70）与 MPU6500（SPI，WHO_AM_I = 0x70）开机自检识别。
  • 软件轴重映射：SwapXY / FlipX / FlipY / FlipZ 四个开关适配不同模块的贴装朝向，换 IMU 不用改驱动。
  • 自动水平校准：上锁状态下检测到静止满 400 ms，自动以加速度计读数重置水平参考并同步给三个解算器。

2.3 安全保护

  • 8 种故障保护原因统一编码（IMU 失效 / dt 超限 / 倾斜超限 / 遥控超时 / WS 断连 / KILL / 手动上锁 / 电机硬件故障），全部收敛到唯一的 disarmNow() 出口。
  • 解锁四条件互锁 + 800 ms 保持时间：油门、摇杆回中、机身姿态端正、无故障，缺一不可且需持续保持，杜绝误解锁。
  • 故障后锁定需显式解除：必须先关闭解锁开关且油门归零，才能回到可解锁状态，防止故障抖动引发反复解锁。
  • 低油门强制停转：油门 ≤ 0.05 时直接关电机并复位全部 PID，清理悬停临界区积累的积分。
  • 三重 NaN 防护：IMU 读数失败、姿态解算出 NaN/Inf、PID 输出 NaN，三处独立判据，任一命中立即上锁，阻断 NaN 向电机输出的传播。
  • 电机测试三重闸门：输出 ≤ 20% 油门、时长钳位 100~2000 ms、已解锁 / 电机故障 / 摇杆有输入时直接拒绝执行。

2.4 人机交互

  • 飞控自建 WiFi 热点（默认 YaoKun_Drone / 12345678，IP 192.168.4.1），野外无网环境照样能飞。
  • 零依赖单页界面：HTML / CSS / JS 全部编译进固件（1651 行），不引用任何 CDN 或图片资源，断网可用。
  • 双虚拟摇杆：左杆油门 / 偏航，右杆俯仰 / 横滚，Pointer Events 同时支持鼠标与触摸，摇杆释放时三轴自动回中而油门保持。
  • 20 Hz 固定节拍发包：与界面渲染帧率彻底解耦，手机掉帧或浏览器后台节流都不会导致飞控侧判定指令超时。
  • 三色状态灯语义：红灯 / 绿灯常亮 = 已解锁；同步呼吸 = 上锁待机；120 ms 快闪 = 故障；蓝灯快闪 = 正在飞行，常亮 = 网页已连接，慢闪 = 待机。
  • 14 种蜂鸣音效：上电、就绪、解锁成功长鸣、双短鸣（陀螺标定）、三短鸣（水平标定）、起飞提示（次数 1~10 可调）、急促故障报警、三级电压告警、紧急停止专用音，并支持全局静音。完整节奏谱与触发场景见第九章。
  • 三级电池电压告警：3.70 / 3.50 / 3.30 V 三档阈值，灯光与蜂鸣节奏同步递进，告警优先级高于飞控状态灯。
  • 12 套主题配色（浅色 / 暗黑 + 10 种中国传统色），选中项存入浏览器 localStorage，下次打开自动恢复。

2.5 参数与可维护性

  • 多板型条件编译：config.h 中改一行宏即可切换 PCB，引脚完全隔离互不干扰。
  • 全参数在线可调：9 个 PID 增益 + 7 项飞行限值 + 滤波器模式 + 蜂鸣器设置，全部 Web 端热更新并持久化到 NVS。
  • 参数双重限幅：写入时钳位一次，从 NVS 读出后再钳位一次，防止旧固件残留值造成越界。
  • 五组临界区保护共享状态：遥控指令、配置 / PID、KILL 请求、电机测试、校准请求，FreeRTOS 双上下文下无竞争。
  • 命令全部有 ack 应答：参数没生效、命令被拒绝（如已解锁时下发校准）都能在界面上立刻看到原因。

三、系统架构

整套固件按职责切成五层，层与层之间只通过 drone_types.h 中声明的接口通信，不存在跨层直接操作。这让「换一块 PCB」「改一个算法」「重写整个界面」都可以各自独立进行，互不牵连。

为什么要分层？本项目支持多种 PCB 板型（4 种已实现、4 种规划中），而板型差异只体现在 config.h 的引脚定义里。若硬件访问散落在算法代码中，换板型就要翻遍全工程。把所有 ledcWrite、Wire.begin、SPI.transfer 收敛到 hardware.ino 之后，上层算法完全不知道自己跑在哪个引脚上——这是本工程能以单份代码覆盖多板型的前提。

3.2 代码规模分布

四、控制主流程

loop() 被刻意做成极简：刷新 LED、推进蜂鸣器状态机，然后检查是否到了控制周期。没到就 delayMicroseconds(50) 空转，让出 CPU 给 WiFi 任务；到了就以累加器方式补偿时间基准，把滞后的时间槽一次补齐，然后进入 controlStep()。

// 时间基准与补偿：即使某一周期超时，也不会让后续周期永久漂移
if ((int32_t)(now_us - next_us) >= 0) {
    while ((int32_t)(now_us - next_us) >= 0) next_us += kLoopPeriodUs;
    const float dt = (now_us - last_us) * 1e-6f;
    last_us = now_us;
    controlStep(dt);
    // …电压告警 200 ms、蓝灯 50 ms、告警 LED 覆盖
} else {
    delayMicroseconds(50);
}

4.1 优先级编排：为什么是这个顺序

这个流水线的顺序不是随意排的，每一步都在为「万一前面已经出问题了，后面不该再执行」服务：

次序环节为什么放在这个位置
①KILL 请求最高优先级。用户按下「紧急上锁」时，即使此刻电机正在转、IMU 已经失灵，也必须立刻停机，不能被后续任何判定阻挡。
②电机测试模式一旦进入测试就要跑完整个时长，中途被飞行逻辑插一脚会造成电机忽转忽停。所以它抢在控制逻辑之前，且结束后直接 return。
③dt 有效性dt 异常意味着调度被长时间阻塞，此时算出的任何控制量都不可信，必须先停下来说明原因。
④IMU 读取没有姿态数据就无从控制。注意 IMU 读不到就 return，绝不拿上一周期的旧姿态凑合——那会让飞机"凭记忆"飞。
⑤⑥姿态 NaN 校验
倾斜保护		两者都在解算之后立刻判定，早于解锁状态机。原因很实际：如果飞机已经翻倒或姿态发散，此时进入解锁流程毫无意义。
⑦遥控超时指令龄期超限说明操纵者已经失去控制能力，属于"不该继续飞"的信号，排在解锁判定之前。
⑧解锁状态机只有确认"应当处于飞行状态"之后，才进入 PID 与混控。上锁状态下依然发送遥测，保证界面随时能看到状态。

一个容易被忽略的正确设计：安全路径上每一次上锁后都会调用 sendTelemetry() 再 return。也就是说即使飞机正在故障，Web 界面依然能实时看到故障原因。很多飞控在保护状态下就哑了，用户只能盲猜哪里出了问题。

4.2 上电启动时序

两个不可省的等待：

① 陀螺零偏标定约需 1~2 秒（500 次采样 × 2 ms）。标定期间飞机必须绝对静止——若在转动，零偏会被记成角速度，飞机上电后认为自己正在自旋，一推油门就会猛甩。

② IMU 探测失败会直接停机：begin() 返回 false 时 setup 进入 while(true) delay(1000) 死循环。这是刻意设计——没有姿态数据时飞控不可能安全，绝不放行让用户以为"能飞"。

电机 LEDC 绑定失败则不同：它只置 FS_MOTOR_FAIL 标志并禁止解锁，系统继续运行。因为此时 IMU、姿态解算、Web 界面全部正常，用户还有机会打开网页读日志定位问题，直接死循环反而失去诊断手段。

五、控制算法详解

5.1 为什么要串两个环

单环控制的根本矛盾在于：角度误差和角速度误差需要不同的增益量纲。飞控里直接用「角度误差 × Kp」去出电机扭矩，会出现典型的两难——

  • 想要响应快 → 调大 Kp → 电机打满饱和 → 一出小角度就直接满油门，没有任何缓冲余量；
  • 想要动作柔和 → 调小 Kp → 响应迟钝，稍微快点的手法就变成大幅振荡。

串级把这两个诉求拆到两个不同量纲的环上：

  • 外环（角度环）：输入是"角度差多少度"，输出是"应该转多快（°/s）"。它的输出限幅 ±250 °/s 相当于一道天然的速度安全阀——机体最多以 250 °/s 的角速度去追目标姿态，这个速度本身是安全的。
  • 内环（角速率环）：输入是"角速度差多少 °/s"，输出是归一化扭矩。它工作在一个「跟随」问题上，只需把内环稳定地拉住，姿态转换就变得可控而线性。

这是 Betaflight / PX4 等主流飞控都采用的经典结构，不是本项目的发明。但多数教程讲到「串级 PID」就停了，本工程把每个环的量纲、限幅值和整定思路都写在代码注释里，可以逐行对照理解。

5.2 偏航为何只用单环

偏航没有角度外环。因为本机没有磁罗盘、没有任何绝对航向参考，偏航角是陀螺仪纯积分出来的，误差会随时间无限制漂移。给一个会漂移的量设外环，等于给积分漂移又套一层积分，稳态误差反而更糟。所以偏航直接采用角速率单环（g_yaw_rate_pid），把「指令要转多快」这件事直接做对，不去管最终转到哪个朝向。输出限幅 ±0.3，比横滚俯仰的 ±0.5 更保守——因为偏航只影响两个电机，权限小一点更安全。v1.1 起偏航环带有小积分（Ki=0.005），用积分项自动抵消电机/桨扭矩不对称的合力，消除匀速自旋（见 5.5 节说明）。

5.3 X 型混控矩阵

yaw_t = yaw_torque * kYawTorqueSign   // 偏航符号适配系数（见下方说明）
M0 左前 FL = throttle + roll_torque + pitch_torque - yaw_t
M1 右前 FR = throttle - roll_torque + pitch_torque + yaw_t
M2 右后 RR = throttle - roll_torque - pitch_torque - yaw_t
M3 左后 RL = throttle + roll_torque - pitch_torque + yaw_t

符号的来历：横滚靠对角电机差速（FL+RL 增、FR+RR 减产生右倾），俯仰靠前后电机差速，偏航靠同侧反向旋转（左侧减、右侧增产生偏航）。三者叠加后再限幅到 [0, 1]。

偏航符号为什么要乘系数：混控默认约定电机旋向为「左前=逆时针、右前=顺时针、右后=逆时针、左后=顺时针」（对角两两同向）。而 v1.1 实测装机的旋向恰好每颗都相反（左前 GPIO16=顺、右前 GPIO6=逆、右后 GPIO5=顺、左后 GPIO15=逆，对角仍两两同向）——这种布局本身合法，但偏航反扭矩方向整体翻转：不翻转符号时偏航环变成正反馈，起飞后机头越转越快、配合倾斜后推力矢量绕圈，表现为「加速自旋 → 螺旋升天」。解决方式是在 PID 输出之后、进混控之前乘 kYawTorqueSign = -1（config.h）：翻转点选在这里，摇杆杆向、遥控器通道方向、姿态球全部不用改；横滚/俯仰扭矩只与电机位置有关，位置没变故不受影响。

混控符号必须和实际电机安装方向一致，否则偏航环会失效甚至正反馈——表现为起飞后匀速自旋（布局对角同向但整体反向）或加速自旋螺旋升天（相邻同向的非法布局，任何混控都救不了）。首次装机请务必「不装桨」用「测试」页逐个确认电机转向（见第十二节第 4 步），再决定是调电机线序还是改 kYawTorqueSign。详见 第十二节 使用方法第 3 步。

5.4 低油门扭矩缩放

const float torque_scale = clampf(cfg.torque_scale_min + throttle * cfg.torque_scale_slope, 0.0f, 1.0f);
// 默认 = 0.20 + throttle × 2.0
roll_torque  = g_roll_rate_pid.update(...)  * torque_scale;

为什么需要它：无刷电调在低油门区存在明显的死区与非线性。悬停时油门在 30% 上下，正是线性最差的区域，直接输出 0.1 的扭矩差，实际转速差可能只有 0.02——摇杆推到底飞机几乎没反应，"手感发死"。乘上缩放系数后（30% 油门时 scale ≈ 0.8），同样的 PID 输出能换来更明显的实际转速差，微调就灵活了。

代价是高油门时缩放系数会超过 1 被钳到 1，等于不做补偿——这正是想要的：高速时本来就不需要额外放大，否则容易振荡。

5.5 PID 参数默认值

控制器默认 Kp / Ki / Kd输出限幅物理含义
角度环（横滚 / 俯仰共用）2.0 / 0.001 / 0±250 °/s输出是期望角速度，单位 °/s
角速率环（横滚 / 俯仰共用）0.025 / 0 / 0.0002±0.5输出是归一化扭矩，无量纲
偏航角速率环0.030 / 0.005 / 0±0.3限幅更保守，因只影响两电机

注意外环 Ki = 0.001 很小——这是有意的。姿态环的稳态误差本来就由重力静力学自然补偿（机体倾斜时重力本身产生恢复力矩），过大的积分反而会在持续倾斜时积累大量风控量，退出倾斜时产生严重过冲。横滚/俯仰的角速率环完全不用积分（Ki = 0），因为陀螺零偏在标定阶段已经被减掉了。

偏航环的 Ki = 0.005 是 v1.1 新加的（此前为 0）。偏航是单层角速率环，没有外环兜底，而四颗电机与桨的扭矩永远不可能完全对称——这个不对称合力需要一个恒定的反向扭矩去抵消。纯 P 控制器消除稳态扰动的唯一方式是「保留一点残余转速」：转起来产生误差、P 项输出反扭矩与之平衡，于是飞机会匀速缓慢自旋（近地面地效还会放大不对称）。加入小积分后，I 项约 1 秒内即可积出抵消不对称所需的反扭矩，自旋消失；PID 类自带「输出限幅时积分 ×0.99 衰减」的抗饱和机制，不会积爆。⚠️ 从 v1.0 升级且板子里保存过参数的用户：请到网页把偏航 Ki 手动改为 0.005（或点「恢复默认」）；整片刷写会清 NVS，新默认自动生效。

六、姿态解算

6.1 加速度计信任度：整套解算的"理智开关"

这是本工程在姿态估计上最值得说的一处设计。加速度计能测重力方向，陀螺仪能测角速度，两者是互补的——但加速度计只在"没有额外加速度干扰"时才可信。飞机一拉升，加速度计读到的是「重力 + 推力加速度」的合力，方向就不再代表水平面了；如果此时还拿它去修正姿态，就会把不该有的修正加进去，姿态越修越偏。

const float acc_norm = sqrtf(ax*ax + ay*ay + az*az);
const float dev = fabsf(acc_norm - 1.0f);        // 偏离 1g 多少
if (kAccTrustLo > kAccTrustHi)
    acc_trust = (kAccTrustLo - dev) / (kAccTrustLo - kAccTrustHi);   // 线性映射到 0~1
acc_trust = clampf(acc_trust, 0.0f, 1.0f);
参数值含义
kAccTrustHi0.08偏离小于 0.08 g 视为完全可信，trust = 1
kAccTrustLo0.35偏离大于 0.35 g 视为完全不可信，trust = 0（纯陀螺积分）

trust 随后被送进两个地方：Madgwick 的 β 线性插值（β = 0.02 + trust × 0.12）、互补滤波的 α 动态下调，以及 Mahony 的 PI 修正项整体乘以 trust。三套解算器因此共享同一个"该信谁"的判断，行为一致。

6.2 三套解算器对比

解算器状态算法要点适用场景
Mahony默认 用外积计算姿态与重力方向的误差向量 e，以 g' = g + Kp·e + ∫Ki·e dt 修正角速度再积分四元数。积分限幅 ±0.35 rad/s，自旋超 180 °/s 时冻结积分防止发散。 默认选择。计算量适中、参数少、对零偏不敏感，与 Betaflight 同源，资料多。
Madgwick可选 梯度下降法，把重力对齐问题写成目标函数，用 β 步长做梯度下降。β 自适应插值到 0.02~0.14。加速度模长过小时自动切纯陀螺积分。 想自己调 β 感受"信任度"效果时；需要理解梯度下降的读者。
互补滤波可选 最朴素：陀螺积分 + 加速度 atan2 直接求角，按 α = 0.98 一阶互补。α 随 trust 动态上调（更信陀螺）。 教学首选，公式最直观；也是验证另两套是否出问题的对照组。

切换时如何保持姿态连续？若直接换解算器，新解算器内部四元数还是单位四元数（水平），而飞机实际已经倾斜了几十度——切换瞬间姿态会突然"跳回零"，控制环立刻输出满扭矩把飞机抽飞。所以代码里先把旧解算器的当前欧拉角取出来，用 setEulerDeg() 注入新解算器，互补滤波则直接接管内部状态，三者对齐后再继续。这是本工程里一个容易被忽略但至关重要的细节。

6.3 水平校准的两条路径

方式触发条件行为
手动校准「设置」页点击按钮（须上锁，发 CAL,LEVEL）读取当前加速度计解算的水平角存入 g_level_roll_offset_deg / g_level_pitch_offset_deg，立即存 NVS，三短鸣确认
自动校准上锁 + 静止满 400 ms（加速度模长偏离 < 0.10 g 且三轴角速度 < 1.5 °/s）用加速度计读数覆盖解算姿态，并同步重置三个解算器与互补滤波内部状态

输出姿态始终是「解算值 − 校准偏置」，所以偏置只存一次、长期生效。偏航偏置变量虽然存在（g_level_yaw_offset_deg），但当前 UI 没有写入入口，恒为 0。

换 IMU 模块后必须重跑水平校准。不同模块的贴装朝向和零偏都不同，校准偏置是绑定在"这块板子 + 这个模块"上的。换模块不清零，姿态球会持续歪着，自动校准也会一直按错误基准重置。

七、安全机制

7.1 统一上锁出口

无论从哪条路径发现故障，最终都调用同一个函数 disarmNow(reason)。它按固定顺序做七件事：

  1. 清除已解锁标志 g_armed = false
  2. 四个电机 PWM 全部写 0
  3. 复位全部 5 路 PID（清零积分与微分历史）
  4. 置解锁禁止标志 g_arm_inhibit = true
  5. 记录故障原因到 g_last_fs 并写状态消息
  6. 蜂鸣短鸣（KILL 用专用音，因为 KILL 已经播过 BUZ_KILL）
  7. 停止任何循环报警音

为什么坚持"单一出口"？如果每个故障分支各自写一套关电机逻辑，早晚会有某个分支忘了清积分或者忘了停报警音。用户看到的现象是"电机停了但蜂鸣器还在尖叫"或者"解锁后飞机猛地一抽"——这类 bug 极难定位。收敛到一个函数后，新增故障类型只需加一个枚举值，代码改动量归零。

v1.1 起芯片欠压复位（brownout）已关闭（setup() 首条语句清 RTC_CNTL_BROWN_OUT_ENA，与 Flix 飞控同款做法）。原因：1S 锂电 + LDO 供电压差余量小，四电机满载浪涌会把 3.3V 轨拉到芯片欠压阈值（约 2.43V）以下，触发芯片硬复位——实测表现为「放地上推油到即将离地必重启、手上测试却正常」（临界油门=电流最大时刻）。关闭后软件侧 FS_ 故障码不受影响，但真欠压时芯片不再自保护复位，只剩蜂鸣器三级电压告警（<3.70V 慢鸣 / <3.50V 快鸣 / <3.30V 急促），请飞手留意电压、及时返航。治本方向：供电线加粗、电源加电解电容、或用独立 BEC 给飞控供电。

7.2 解锁状态机

解锁四条件（缺一不可）

条件要求防的是什么
① 油门≤ 0.05（kArmThrottleMax）避免带油门解锁，一解锁电机就猛转
② 摇杆横滚 / 俯仰 / 偏航 |值| ≤ 0.15（kStickCenterMax）避免带着操纵指令解锁，起飞瞬间就偏航
③ 姿态|roll| 与 |pitch| ≤ 45°避免倒着或大角度倾斜时解锁
④ 状态无电机硬件故障、不在故障抑制中避免电机故障后反复尝试解锁

四条件必须连续保持 800 ms（kArmHoldMs）才真正解锁。任何一帧被破坏，计时立即清零重来。这个设计直接针对消费级飞控最常见的事故——"手一碰摇杆开关就解锁起飞"。

7.3 故障后的恢复路径

注意：故障后不会自动恢复可解锁状态。

必须先关闭解锁开关（arm_request = false）且把油门归零，解锁禁止标志才被清除。这个"必须显式复位"的设计是有意的：故障刚发生时，机体姿态、电机状态往往还没稳，让操作者主动做一次"我确认安全了"的动作，比系统自作主张重新允许解锁安全得多。

7.4 三道不进入枚举的额外保护

保护规则
低油门强制停转throttle ≤ 0.05 时直接写 0 并复位全部 PID。悬停临界区最容易积累积分，必须清。
电机测试三重闸门输出 ≤ 20%；时长钳位 100~2000 ms 且到时自动停；已解锁 / 电机故障 / 摇杆有输入时命令直接被拒绝并回 ack。

八、通信与 Web 遥控

8.1 通信链路

飞控上电即开启 SoftAP 并注册三类路由：/ 返回内嵌单页应用，/health 返回 OK（用于探测设备是否在线），/ws 是 WebSocket 端点。浏览器访问 http://192.168.4.1 拿到页面后立刻建立 WebSocket 连接，连接建立瞬间固件就把全量配置推给前端，之后进入 20 Hz 双向循环。

为什么用 WebSocket 文本帧而不是二进制 MAVLink？本工程的定位是"浏览器直连遥控"，操作者就是拿着手机的人而不是地面站。文本 JSON 换来三个实际好处：① 串口助手、浏览器控制台、Python 脚本都能直接收发，调试门槛为零；② 前端解析一行 JSON.parse，不需要引入 mavlink 解析库和消息注册表；③ 没有字节序和字段对齐问题，人肉可读。代价是带宽略高（每帧约 200 字节 × 20 Hz ≈ 4 KB/s），对 WiFi 来说完全无压力。

右摇杆（俯仰 / 横滚）松手时三轴立即归零，回到「姿态自稳」状态；左摇杆的油门则保持当前位置不回零。若油门也回零，飞机会瞬间掉高度。刻意让两个摇杆行为不同，是为了让"松手"这个动作的含义明确——姿态回稳、高度自己掉，操作者心里有数。

九、音效与灯效系统

这套飞控没有屏幕，蜂鸣器和三色灯就是它的「仪表盘」。作者把 14 种提示音和 3 色灯语设计成一套完整的反馈语言：不用连网页、不用看串口，光靠听和看就能知道飞机正处在什么状态、出了什么事。整套系统的实现原则是彻底的非阻塞——所有音效灯效都由 millis() 时间戳驱动的状态机刷新（buzzerUpdate() / ledUpdate() 在主循环里轮询），全程没有一处 delay()，500 Hz 控制循环永远不会被一声「嘀」卡住。

9.1 全流程声光联动

先看一遍从上电到降落的完整生命周期——每个阶段声音和灯光都在配合讲故事：

两条反馈通道各管一摊，互不干扰：红绿灯表达飞控核心状态（启动 / 待机 / 解锁 / 故障），蓝灯表达遥控链路状态（有没有连上网页、是否真的在飞）。这样「灯在快闪」时你不用猜是故障还是飞行——看颜色就分得清。

9.4 设计上的几个讲究

非阻塞状态机

每种音效都是「子状态 + 截止时间戳」的小状态机，由 buzzerUpdate() 轮询推进。任何时刻主循环都不会等一声播完——这对 500 Hz 实时控制是底线要求。

静音只拦「发声」

buzzerSet() 开头检查静音标志：静音时状态机照常推进，只是不驱动引脚。取消静音后一切自然接续，不会出现「静音期间状态卡死」。

循环音单独管理

buzzerStopLoop() 只停 5 种循环音（滴答 / 报警 / 三级电压），不砍刚触发的单次音。所以上锁短鸣不会被紧接着的报警「吃掉」，提示音永远完整。

参数持久化

静音开关与起飞音效轮数在 Web 端设置后写入 NVS（BUZZER_MUTE / TAKEOFF_REPEAT 命令），断电重启自动恢复，不用每次重设。

9.5 想自己加一种音效？三步就够

  1. 注册枚举：drone_types.h 的 BuzzerPattern 里加一项（如 BUZ_CAL_FAIL）。
  2. 写节奏：单次音只需在 buzzerPlay() 的 switch 里给时长；复杂节奏（连击/循环）在 buzzerUpdate() 里加一个 if (g_buzzer_pattern == ...) 分支，用 g_buzzer_sub_state 推进。
  3. 找位置触发：在对应业务点调 buzzerPlay(你的音效)，完毕。

听音辨障速查：一声 200 ms = 上电自检过　·　一声 100 ms = 就绪 / 已上锁　·　两短 = 陀螺校准好　·　三短 = 水平校准好　·　长鸣 = 已解锁（危险）　·　嘀嘀嘀（快）= 故障　·　慢滴滴→快滴滴 = 电压在掉　·　两声急促 = 紧急停止。

十二、使用方法

12.1 首次上电（严格按顺序）

安全提示：首次装机务必拆掉螺旋桨完成下面第 1~4 步。电机转向和混控符号的错误在带桨时会造成炸机。等第 4 步全部通过再装桨。

1
静止放平，上电把飞机放在水平桌面上，保持绝对静止约 2 秒。陀螺零偏标定期间若在转动，零偏会被记成角速度，上电后飞机认为自己正在自旋，一推油门就会猛甩。听到就绪短鸣说明标定完成。
2
确认串口输出正常串口监视器应打印出 IMU 型号识别结果与 Ready. Open http://192.168.4.1/。若停在 IMU init FAILED，说明没识别到传感器——检查 I2C 接线（SDA=9 / SCL=8）或确认模块是否为 MPU6500。
3
连接热点，打开网页，做水平校准手机连 WiFi YaoKun_Drone（密码 48539491）→ 浏览器打开 http://192.168.4.1 → 进「设置」页 → 看姿态球是否水平（不应歪）→ 点「水平校准」听三短鸣 → 若姿态球歪了，切换到互补滤波模式对照看读数，判断是不是 IMU 轴映射错了（见 10.2 节）。
4
逐个测试电机方向（拆桨状态下）进「测试」页 → 依次点 M0 / M1 / M2 / M3，每个给 0.12 油门、600 ms。核对位置：M0 转时是左前、M1 是右前、M2 是右后、M3 是左后；再核对旋向（俯视）：M0 左前=顺时针、M1 右前=逆时针、M2 右后=顺时针、M3 左后=逆时针（对角两两同向，此即 kYawTorqueSign=-1 适配的出厂布局，见 5.3 节）。若位置错了查 config.h 引脚映射；若某颗转向不符，对调该电机两根输出线即可反转。注意：四个电机必须呈「对角两两同向」布局——相邻同向的非法布局偏航控制力矩恒为零，任何软件都无法补救，必须先改硬件。
5
装桨，检查桨向确认四个电机旋向与上表一致（对角两两相反）后装桨。桨型必须与电机旋向配套：顺时针电机装顺时针桨（推力向上），逆时针同理——同一个电机的桨必须是"推力方向一致"，这是最基础也最容易装反的地方。
6
低高度试飞回到「遥控」页 → 油门摇杆缓缓上推一点点到 20~30% 让它离地 → 立刻打「ARM」开关，保持不动 1 秒等解锁成功长鸣 → 微调油门保持高度 → 轻推右摇杆测试横滚 / 俯仰方向是否正确（推右飞机应右倾）。方向反了立刻上锁，修正后重试。

12.2 每次飞行前检查

  • 电池电压充足（> 3.7 V 以上），接线牢固，桨叶无损伤、无松动
  • 上电后等待陀螺标定完成（保持静止）
  • 网页能连上，姿态球水平无漂移
  • 解锁时油门归零、三摇杆回中、机身水平
  • 周围无障碍物，无人站在起降点附近

十三、PID 调参指南

13.1 整定顺序：必须从内环到外环

不要同时调两个环。外环在动，内环的行为就无法判断，你会分不清"反应慢"是外环 Kp 小还是内环跟不上。先把内环调稳，再调外环——这是串级控制的唯一正确顺序。

第一步：先调角速率内环（RATE 组）

先在设置页把角度环 Kp 降到 0.5 左右，让外环变弱，减少干扰。然后：

  • 偏慢（推杆后转速跟不上）→ 提高 Kp
  • 振荡（机身高频抖动）→ 降低 Kp，或增加 Kd
  • 范围参考：Kp 0.015~0.040，Kd 0~0.0005

第二步：再调角度外环（ANGLE 组）

内环稳定后再动外环：

  • 回中太慢、机身软 → 提高角度 Kp
  • 来回摆动振荡 → 降低角度 Kp
  • 总有固定倾角停不住 → 略加 Ki（0.0005~0.002），不要超过 0.005
  • 范围参考：Kp 1.5~3.0，Ki 0~0.002，Kd 一般保持 0

第三步：偏航（YAW 组）

偏航通常不用调，默认值即可工作。若转向有轻微延迟可把 Kp 从 0.030 提到 0.040；不要给偏航加 Ki——航向角本来就在漂，积分只会把漂移放大成持续偏转。

13.2 安全限值的整定

参数默认可调范围整定建议
最大倾角30°5~80°新手保持 20~30°。这是"最大允许倾斜"，直接决定飞机能被压到多平
最大偏航速率180 °/s30~360新手 120~180 足够。太大容易转晕自己
倾斜保护角80°20~85°越低越安全。60~70° 就能有效保护，别为了"能压得更平"往上调
遥控超时300 ms100~2000弱信号环境可适当放宽到 500~800；信号好时别低于 200，否则偶发丢包就上锁
遥测周期50 ms20~500默认 20 Hz 够用。改成 20 ms（50 Hz）会明显增加 WiFi 负担
扭矩缩放0.20 / 2.00~1 / 0~4悬停手感发死就提高 min 或 slope；振荡则降低

每次只改一个参数。改完必须实测并记录，改了三项就分不清是哪项起的作用。所有参数在 NVS 里持久化，不点「保存参数」重启就丢——但在地面调试时建议每次都点保存，避免意外断电丢失配置。

网页打不开 192.168.4.1 没连上热点 / 串口卡住 确认连的是 YaoKun_Drone（不是路由器同名 WiFi）；部分手机会提示"该 WiFi 无法访问互联网"并自动断开，需在设置里选"保持连接"或关闭该提示
网页时好时坏 / 遥测卡顿 多台设备信道干扰 只留一台飞机上电（多机同 SSID 会抢占同一信道）；手机切到飞行模式关掉数据；靠近路由器或改用 5G 频段
改完参数没效果 没点「应用」/ 没点「保存」 「应用」= 立刻生效（仅本次）；「保存参数」= 写入 NVS（重启仍保留）。两个都要点
校准按钮点了没反应 飞机已解锁 校准只允许上锁时进行，先关闭 ARM 开关
电机不转 / 单转 电调没上电 / 油门过低 确认电调 BEC 供电；注意本机 throttle ≤ 0.05 时强制停转，低于 5% 油门必然不转
串口能开网页打不开 固件版本过旧 / 编译未完成 确认已重新编译烧录；本工程 Web 界面对应较新版本固件

通用诊断三步法：① 看串口——有没有 Detected MPU6050/6500 和 LEDC attach: 1 1 1 1；② 看网页遥测——姿态对不对、loop_hz 是否接近 500、fs 是不是 0；③ 拆桨做单电机测试。三步能把九成问题定位到"传感器 / 链路 / 混控"三类。

十五、设计取舍与已知边界

15.1 这套代码做对了什么

设计点价值
单一上锁出口新增故障类型只需加一个枚举值，不存在"某个分支忘了关电机"的漏洞
安全路径也发遥测故障时界面照样实时显示原因，不用盲猜
五组临界区保护FreeRTOS 双上下文下共享状态零竞争，且临界区都很短，不影响 500 Hz 时序
加速度计信任度把"什么时候不能信加速度计"变成显式可计算的量，而不是靠固定权重碰运气
滤波器切换保连续避免切换瞬间姿态跳变导致满扭矩抽飞——这是同类项目里常见的隐蔽 bug
参数双重限幅写入钳位 + 读出再钳位，防止旧固件残留值造成越界
固定节拍发包界面卡顿不影响指令帧率，这是遥控系统稳定性的基础
注释密度极高每个常数有出处、每个非直觉处有"为什么"，可作为中文飞控教材阅读

15.2 诚实的局限性

局限影响与说明
无法定点悬停只有 IMU，没有位置或垂向参考。松杆保持水平速度继续飘，松油门就掉高度。这不是 bug，是传感器配置决定的物理边界。
偏航会缓慢漂移无磁罗盘，偏航角是陀螺纯积分结果，长时间飞行航向会偏。上锁静止时因静止检测会持续校正，飞行中无法校正。
只能浏览器操控SBUS / ELRS 引脚已定义但无驱动实现，当前版本没有实体遥控器支持。
没有黑匣子故障后无法回放飞行数据定位原因。NVS 只存参数，不存飞行日志。
没有地面站协议用 WebSocket 文本 JSON 而非 MAVLink，QGC 等地面站无法直接连接。这是"浏览器直连"定位的取舍。
无 OTA 升级需 USB 重新烧录。
偏航权限偏小输出限幅 ±0.3，比横滚俯仰保守。高速偏航时可能显得"转不动"。
代码未做模块化收尾controlStep()（约 250 行）仍在主文件里，hardware.ino 885 行同时承载四类驱动——能跑能读，但再往上加功能建议先拆分。

+ PMW3901 光流		接 SPI + 第二组 I2C，做"无 GPS 悬停"——这是本机最值得做的升级，能从根本上解决无法定点的短板。原理：光流测水平位移，测距测高度，两者配合就能估计出水平速度并做定点修正。

低MAVLink 协议接入 QGC / Mission Planner。代价是要引入解析库和消息注册表，与当前"零依赖单页应用"的简洁性有冲突，需权衡。
低代码拆分把 controlStep() 拆成独立模块、hardware.ino 按驱动类型分成四个文件。当前 5173 行仍可读，但继续膨胀会失控。

如果只做一件事：做定高（测距或气压 + 双环 PID）。它带来的改变是质变级的——从"手动飞行"变成"能松杆的飞行"，是这个飞控从"能飞"到"好用"的分水岭。
